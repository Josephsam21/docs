LASUMedScreen is optimised for deployment on Vercel, but can run on any platform that supports Node.js 20 and Next.js 15. This page covers the fastest path to production. For advanced build configuration, Docker self-hosting, and full CI/CD pipelines, see [Build & Deploy](/docs/configuration/build-and-deployment).

## Deploy to Vercel

Vercel is the fastest path from repository to production URL. It handles build caching, CDN distribution, and automatic preview deployments for every pull request out of the box.

<Steps>
  <Step title="Push your code to a Git provider">
    Make sure your LASUMedScreen repository is pushed to a GitHub, GitLab, or Bitbucket account. Vercel connects directly to your Git provider to trigger builds on every push.

    ```bash Terminal
    git add .
    git commit -m "Initial commit"
    git push origin main
    ```
  </Step>
  <Step title="Import the repository on Vercel">
    Go to [vercel.com](https://vercel.com), sign in, and click **Add New → Project**. Select your Git provider, find the `lasumedscreen` repository, and click **Import**.
  </Step>
  <Step title="Set the framework preset">
    Vercel should automatically detect Next.js. If it does not, open the **Framework Preset** dropdown and select **Next.js**. Leave the build command and output directory at their default values.
  </Step>
  <Step title="Add environment variables">
    Before clicking Deploy, expand the **Environment Variables** section and add all the variables from your `.env.local` file — replacing every value with your **production** credentials. Use your production Supabase project URL and keys, your verified Resend sending domain, and your live app URL.

    See the [Environment Variables reference](/docs/configuration/environment-variables) for the full list of variables and where to find each value.
  </Step>
  <Step title="Deploy">
    Click **Deploy**. Vercel runs `pnpm build`, performs any output optimisations, and publishes the app to a `.vercel.app` URL. Subsequent pushes to `main` trigger automatic redeployments.
  </Step>
</Steps>

## Production Supabase Setup

Your production deployment must use a dedicated Supabase project that is completely separate from the one you use for development. Sharing a project between environments risks data loss and exposes student medical records to development-level access controls.

- **Create a new project** at [supabase.com](https://supabase.com) specifically for production. Name it clearly, for example `lasumedscreen-prod`.
- **Enable Row Level Security** on every table before going live. RLS ensures that students, doctors, and administrators can only access the rows they are authorised to see, regardless of the API key used.
- **Configure Auth settings** — in your Supabase dashboard go to **Authentication → URL Configuration** and set:
  - **Site URL** to your production domain (e.g. `https://lasumedscreen.youruniversity.edu.ng`)
  - **Redirect URLs** to include all allowed post-auth redirect paths.
- **Run migrations** against your production database using the Supabase CLI:
  ```bash Terminal
  supabase db push --db-url your-production-db-url
  ```
  Replace `your-production-db-url` with the connection string shown in **Settings → Database** in your production Supabase project.

<Warning>
  Never use your development Supabase project in production. Development projects frequently have RLS disabled for convenience, permissive policies, and test data. Create a separate production project with its own URL and credentials, and treat those credentials as highly sensitive.
</Warning>
